# Contributing

The rule for `main`: no change can silently alter existing behavior. Either a check fails, or the
PR diff shows exactly what changed and someone approved it. The plan is in
[docs/mvp-plan.md](docs/mvp-plan.md).

## Setup

Node 22 and pnpm (the version pinned in `package.json`, via `corepack enable` or a global install).

```sh
pnpm install
pnpm build          # web app, then a dry-run bundle of the Worker
pnpm dev            # Vite on :5173 with /api proxied to wrangler dev on :8787
```

| Command                | What it does                                                                |
| ---------------------- | --------------------------------------------------------------------------- |
| `pnpm lint`            | ESLint plus repo policy checks (no em dashes, Playwright image in sync)     |
| `pnpm format`          | Prettier (`pnpm format:check` in CI)                                        |
| `pnpm typecheck`       | `tsc` in every package (`@pp/core` src is checked with no DOM or Node)      |
| `pnpm test`            | Vitest: `@pp/core` unit, property and golden (with coverage); web; Worker   |
| `pnpm perf`            | Vitest benchmarks checked against `packages/core/bench/budgets.json`        |
| `pnpm e2e`             | Playwright against local `wrangler dev` (run `pnpm build` first)            |
| `pnpm golden:update`   | Rewrite golden snapshots and `golden-summary.md`                            |
| `pnpm fixtures:record` | Re-record the ORS fixtures with a real key (`ORS_API_KEY` in the env)       |
| `pnpm visual:update`   | Regenerate screenshot baselines in the Linux Playwright container           |
| `pnpm lighthouse`      | Lighthouse accessibility, phone and desktop (run `pnpm build` first)        |
| `pnpm icons`           | Render the app icons in `apps/web/public/icons` from `apps/web/icons/*.svg` |
| `pnpm races:add`       | Add a race's course to the race library (see [Race library](#race-library)) |
| `pnpm rollback`        | Roll production back to the previous Worker version (`--dry-run` to check)  |

## Test layers

| Layer               | Tool                                   | Where                                           | Runs                            |
| ------------------- | -------------------------------------- | ----------------------------------------------- | ------------------------------- |
| Unit and property   | Vitest                                 | `packages/core/test/*.test.ts`                  | Every PR                        |
| Web unit            | Vitest (store, sheet math, worker RPC) | `apps/web/test/*.test.ts`                       | Every PR                        |
| Golden snapshots    | Vitest                                 | `packages/core/test/golden-cases.ts`            | Every PR                        |
| Worker integration  | Vitest + `@cloudflare/vitest-plugin`   | `apps/worker/test`                              | Every PR                        |
| Performance budgets | Vitest bench, Playwright `performance` | `packages/core/bench`, `e2e/tests/perf.spec.ts` | Every PR (over budget fails CI) |
| E2E                 | Playwright (desktop, iPhone, Pixel)    | `e2e/tests`                                     | Every PR, against the preview   |
| Visual regression   | Playwright `toHaveScreenshot`          | `e2e/tests/visual.spec.ts`                      | Every PR                        |
| Accessibility       | axe in Playwright                      | `e2e/tests/a11y.spec.ts`                        | Every PR                        |
| Accessibility score | Lighthouse (at least 95)               | `e2e/scripts/lighthouse.mjs`                    | Every PR                        |
| PWA                 | Playwright, service worker on          | `e2e/tests/pwa.spec.ts`                         | Every PR                        |
| Live smoke          | Playwright `@smoke` and `@live`        | `e2e/tests`                                     | Nightly and after each deploy   |

"Every PR" means before merge, in the PR's full CI run; pushes in between get a quicker subset
(see [Quick and full runs](#quick-and-full-runs)). Firefox and WebKit run weekly.

Rules of thumb:

- `@pp/core` has a 90% line and branch coverage floor. The UI relies on E2E tests instead.
- Randomized tests always use a fixed seed (`packages/core/test/support/rng.ts`) and print it on failure.
- Fixtures are committed and never fetched at test time. Only `@live` tests (nightly) touch the network.
  E2E serves map and DEM tiles from fixtures (`e2e/support/app.ts`), and answers `/api/route` from the
  ORS fixtures through the Worker's own parser (`e2e/support/draw.ts`), so drawing tests need no key.
  E2E tests open the app with `openApp` (`e2e/support/app.ts`), which serves the basemap TileJSON from
  `e2e/fixtures/openfreemap` and answers every tile and glyph request with an empty response.
- Every bug fix starts with a failing E2E or golden test that reproduces it.
- Tag tests that are safe against production `@smoke`, tests that need real third-party services `@live`.
- With `PP_BROWSERS=all` the suite also runs on Firefox and WebKit (nightly). Headless Firefox has
  WebGL for the map only with an X display, so on Linux run it as `xvfb-run pnpm e2e`. A test that
  needs Chromium-only tooling (the DevTools protocol: touch drags, safe-area insets, Chrome's
  installability check) skips elsewhere with its reason and a link to
  [#42](https://github.com/jcj59/perfect-pace/issues/42).

## Golden snapshots

Each case in `packages/core/test/golden-cases.ts` writes `packages/core/test/golden/<name>.json`, and
all of them roll up into `golden-summary.md` for a readable diff. Round every number with the
stated precision in `test/support/precision.ts` (1 m distance, 0.1 m elevation, 0.1 s pace).

`pnpm test` fails when a snapshot is stale, missing or orphaned, or the summary is out of date. To
accept a change on purpose:

```sh
pnpm golden:update
git diff packages/core/test/golden   # review it
```

The PR description must say why the outputs changed.

## Visual baselines

Baselines live in `e2e/tests/__screenshots__/<project>/` and are only ever generated in the
official Linux Playwright container (`mcr.microsoft.com/playwright:v<version>-noble`), the same
image the CI `e2e` job runs in, so they match pixel for pixel. Local `pnpm e2e` runs skip screenshot
assertions (set `PP_VISUAL=1` to force them).

```sh
pnpm visual:update        # with Docker: regenerates baselines locally in the container
pnpm visual:update --ci   # without Docker: labels your pushed branch's PR `visual-update`, which
                          # runs the "Visual baselines" workflow, and downloads its output here
```

Commit the new PNGs and give the reason in the PR description. A missing baseline fails CI. When
bumping `@playwright/test`, bump the container image tags in `.github/workflows` to match (`pnpm
lint` checks) and regenerate the baselines.

## Performance budgets

Every benchmark in `packages/core/bench/*.bench.ts` needs an entry in `bench/budgets.json` (its
`file > group > name` key and a `maxMedianMs`), and every budget needs a benchmark. Browser budgets
read `performance` marks in `e2e/tests/perf.spec.ts`, and timing budgets that must not share the CPU
with other tests run in their own projects, one after another once the others finish: the 50k-point
course load (`load-perf`, `e2e/tests/load-perf.spec.ts`), then the marathon plan recompute
(`plan-perf`, `e2e/tests/plan-perf.spec.ts`). Raise a budget only with a reason in the PR.

The course load budget (B1: a 50k-point file in under 1 s on a mid-range laptop) is scaled to the
machine it runs on, because hosted runners differ: on the same code the older ones (AMD EPYC 7763)
take about 1.3x as long as the common one (EPYC 9V74), and the newest (EPYC 9V45) about 0.75x.
Before and after each load the test runs a calibration workload in the same page
(`e2e/support/calibrate.ts`: GPX-like text written and scanned, numbers parsed, an object per
point, haversine sums, typed arrays), and the budget is `1000 ms x calibration / 45 ms`, never
below 1000 ms and at most 2x. 45 ms is what the EPYC 9V74 takes, about a mid-range laptop's single
core (a recent high-end laptop takes about 25 ms), so a machine at least that fast is held to the
plain 1000 ms, and that includes every local run on a laptop. A runner that is slower but not 2x
slower gets proportional headroom, and one past 2x fails, since it cannot say anything about the
budget. Like the benchmarks, the test holds the median of three loads, each in a fresh browser
context; it logs every load with its phases (read and parse in the worker, the line handed to the
map, drawn), the calibration and the budget it used. Recalibrate `REFERENCE_CALIBRATION_MS` only
when the workload changes, from a run's logs on the common runner.

## Flaky tests

No blanket retries. Playwright gets one retry in CI, and a test that passes only on retry shows up
as flaky in the report. Within the same week, either fix it or tag it `@quarantine` and link an
issue. Quarantined tests still run in CI in a separate, non-blocking step.

## CI and deploys

| Workflow           | Trigger                                    | What it does                                                                                                          |
| ------------------ | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `CI`               | every PR push, `full-ci` label, manual     | a quick, full or docs run (below): `verify`, `perf`, `preview` (alias `pr-<n>`), `e2e`, `lighthouse`                  |
| `Full CI`          | `full-ci` PR label added                   | re-runs the head commit's `CI` run, which then runs in full (a label event cannot start one by itself)                |
| `Deploy`           | push to `main`                             | deploy production, smoke test it, roll back and open an issue on failure                                              |
| `Nightly`          | daily 07:17 UTC; Mondays 08:17 UTC; manual | daily: live smoke against production. Mondays and manual: full E2E on Firefox and WebKit, 4 shards                    |
| `Visual baselines` | `visual-update` PR label, manual           | regenerate screenshot baselines, one runner per project, merged into one artifact (used by `pnpm visual:update --ci`) |

The required checks on `main` are `verify`, `perf`, `preview`, `e2e` and `lighthouse` (branch
protection; the branch need not be up to date). `e2e` includes the axe checks (`a11y.spec.ts`,
every key screen in both themes, including offline and keyboard drawing), the visual and PWA
suites and the timing budgets; `lighthouse` fails below an accessibility score of 95. Playwright
traces, videos and screenshot diffs are uploaded as artifacts when a test fails.

### Quick and full runs

Pushes to a PR get a **quick run**, and the **full run** is what merging needs:

| Run   | When                                                                        | What runs                                                                                        |
| ----- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| quick | every push (opened, synchronize, reopened) without the `full-ci` label      | `verify`, `perf`, `preview`, the `desktop` E2E project (visual and axe included) on 3 shards     |
| full  | the PR has the `full-ci` label, is marked ready for review, or a manual run | `verify`, `perf`, `preview`, `desktop`, `iphone` and `pixel` on 8 shards, `e2e-perf`, Lighthouse |
| docs  | every changed file is `docs/**` or a root `.md`                             | `verify`; the rest is skipped and `e2e` and `lighthouse` pass                                    |

A quick run reports `e2e (quick)` and `lighthouse (full run only)` instead of `e2e` and
`lighthouse`, so on its commit those two required checks stay "Expected" and the PR cannot be
merged. Only a full run that passes on the PR's head commit turns them green, and any new push
needs its own full run. A quick run's `e2e (quick)` still fails when a desktop test fails, and its
summary says how to start the full run.

To start the full run when the PR is ready (agents too, after their last planned push):

```sh
gh pr edit <n> --add-label full-ci   # full run now, and on every later push
```

Adding the label re-runs the head commit's CI run (the `Full CI` workflow cancels it first if it is
still going), and that run's `changes` job reads the PR's labels again, so it runs in full. Any
later re-run of that commit's run (for example "Re-run all jobs" in the Actions tab) also runs in
full while the label is on. Marking a draft PR ready for review starts a full run too. Remove the
label to go back to quick runs. Renovate's PRs get the label automatically (`renovate.json`), so
they auto-merge only after a full run. A manual run (`gh workflow run ci.yml --ref <branch>`) is
always full, but its checks do not show on a PR (GitHub lists a PR's checks from its
`pull_request` runs), so use the label for PRs.

Every run of a PR shares one concurrency group, so a new push (or a full run dispatched for the
PR) cancels the run it supersedes. `CI` runs only for PRs and by hand, never on pushes to
branches, so a commit is not tested twice; pushes to `main` only deploy.

### How a CI run is laid out

Every job starts once `changes` (a few seconds) has picked the kind of run; E2E and Lighthouse also
wait for `preview` (seconds):

| Job              | What it does                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| `changes`        | picks quick, full or docs, and the E2E projects and shards for it                                                    |
| `verify`         | lint, format, Worker types, typecheck, unit/golden/Worker tests, build                                               |
| `perf`           | Vitest benchmarks against their budgets (skipped on docs)                                                            |
| `preview`        | builds and uploads the `pr-<n>` preview version (skipped on docs; does nothing without Cloudflare secrets)           |
| `e2e shard i/n`  | full: desktop, iPhone and Pixel over 8 runners (`--shard i/8`); quick: desktop over 3                                |
| `e2e-perf`       | full only: the `load-perf` and `plan-perf` budgets, one at a time on a runner of their own                           |
| `e2e`            | the required check: every shard and `e2e-perf` passed (full) or only docs changed; `e2e (quick)` in a quick run      |
| `e2e-report`     | merges the shards' blob reports into one HTML report (full runs, and quick runs that failed)                         |
| `lighthouse-run` | full only: Lighthouse accessibility (at least 95, phone and desktop) on the preview                                  |
| `lighthouse`     | the required check: `lighthouse-run` passed (full) or only docs changed; `lighthouse (full run only)` in a quick run |

Each shard is a full Playwright run in the Playwright container, with one worker (the 2-vCPU
runner's default; two workers were only 1.4x faster and stretched each test by 40%) and the same
single retry, so a test behaves as it did unsharded. On failure a shard uploads its traces and
videos as `playwright-shard-<i>-<attempt>`. The budget projects cannot share a shard: they depend
on the three device projects, so Playwright would pull all of those into the same shard.

To add capacity as the suite grows, raise the shard counts in the `changes` job. Measured on
real runs on 2-vCPU `ubuntu-latest` with 398 tests (before: the last green PR 12 run; after: the
sharding PR on two runs once PR 12 was merged into it):

| Job                   | Before (one E2E job)  | After (sharded)                    |
| --------------------- | --------------------- | ---------------------------------- |
| `verify`              | 1.9 min               | 0.9 to 1.9 min (Turbo cache)       |
| `perf`                | 0.7 min               | 0.7 min                            |
| `preview`             | 0.4 min, after verify | 5 s, at the start                  |
| E2E                   | 20.0 min, after both  | 2.8 to 6.0 min per shard, parallel |
| `e2e-perf`            | inside E2E            | 1.5 to 1.9 min, parallel           |
| `e2e` check green     | 22.4 min              | 4.9 to 6.2 min                     |
| Whole run, wall clock | 22.5 min              | 5.2 to 6.7 min                     |

On the 335-test suite before PR 12, the same change took a run from 19.2 to 5.3 minutes.

### What CI costs

Billed minutes are the sum over a run's jobs of each job's minutes, rounded up per job (how GitHub
bills, though Actions are free on this public repository); skipped jobs cost nothing. Measured on
real runs on 2026-11-15 (before: PRs 17, 18 and 19 and the docs-only phase 2 plan PR; after: this
change's PR #37 and its probe PRs #38 and #39):

| Run                                     | Before                                   | After                                                     |
| --------------------------------------- | ---------------------------------------- | --------------------------------------------------------- |
| A push to a PR                          | full suite every push: 50, 56, 57, 63    | quick: 14, 16, 16, 16                                     |
| The full suite on the PR's final commit | (the last push's run)                    | full: 37, 37, 38, 39, plus 1 for the `Full CI` re-run job |
| A docs-only push                        | 5                                        | 4                                                         |
| A PR with 5 pushes, same hour's runners | 5 x 37 = 185 (no lighthouse gate job)    | 4 x 16 + 38 + 1 = 103                                     |
| Cross-browser (Firefox, WebKit)         | daily: 33 (one job, timed out at 30 min) | weekly: 52 over 4 shards (with today's Firefox failures)  |
| Live smoke                              | daily: 2                                 | daily: 2                                                  |

Runner speed varies by the hour: the same full suite billed 50 to 63 minutes in the morning's runs
and 37 to 39 in the evening's, so compare quick and full runs from the same hour. A quick run is
about 40% of a full run: 6 or 7 of its minutes are one-minute floors on jobs that take seconds
(`changes`, `preview`, the two gates), and its 3 desktop shards bill 8 or 9. The weekly
cross-browser run had every Firefox test failing (each one retried, 17 s apiece), so a green run
should cost less.

Where a full run's minutes go: each shard spends about a minute on overhead (30 to 45 s pulling the
Playwright container, 20 s installing dependencies from the pnpm cache, a few seconds building and
saving caches) and 3 to 5 minutes testing, so a desktop-only quick run on 3 shards does a third of
the testing with 3 rather than 8 shards' overhead.

Deploys need two repository secrets: `CLOUDFLARE_API_TOKEN` (a token from the "Edit Cloudflare
Workers" template) and `CLOUDFLARE_ACCOUNT_ID`. Without them the `preview` job skips the deploy and
`e2e` runs against a local `wrangler dev` instead, and `Deploy` skips.

A third, optional secret, `ORS_API_KEY`, is the OpenRouteService key `/api/route` uses (see
[Routing](#routing)). `Deploy` uploads it to the Worker with each production version, previews
inherit it, and `Nightly` runs the live routing test only when it is set. Without it nothing fails:
`/api/route` answers `503 not_configured` and the live routing test is skipped with a warning.

Two more optional secrets, `GITHUB_REPORT_TOKEN` and `TURNSTILE_SECRET`, are what `/api/report`
needs (see [Reports](#reports)). `Deploy` uploads each one that is set, the same way; without them
nothing fails, and the app's report dialog says reporting is unavailable.

To exercise the rollback path without touching production traffic, run the `Deploy` workflow by
hand with "force smoke failure" and "dry run" checked, or locally:

```sh
DRY_RUN=1 PP_FORCE_SMOKE_FAIL=1 bash scripts/post-deploy-smoke.sh <production-url> <live-version> <previous-version>
```

## PWA and offline

The app is installable and works offline for uploaded GPX courses. The pieces:

- **Manifest and icons:** `apps/web/public/manifest.webmanifest`, and PNG icons rendered from the
  SVG sources in `apps/web/icons` (`pnpm icons`, which uses the E2E suite's Chromium; commit the
  PNGs). `favicon.svg` is a copy of `icons/icon.svg`.
- **Service worker:** `apps/web/src/sw/sw.ts`, built to `/sw.js` by `precachePlugin`
  (`apps/web/precache-plugin.ts`), which fills in the precache list (every built and public file,
  plus `/`) and a version hash of their contents. The routing rules are in `src/sw/policy.ts`
  (unit tested in `apps/web/test/sw-policy.test.ts`):
  - Hashed files and icons: from the version's precache first.
  - Navigations: network first, so an online reload always gets the latest build; the cached shell
    answers when offline or after 4 s. Share links live in the hash, so they are navigations to `/`.
  - Terrarium DEM tiles: a least recently used cache of at most 256 tiles (about 25 MB).
  - Never cached: `/api/*`, non-GET requests, the basemap, and files not in the precache (the
    Worker answers a missing `/assets/` file with the app's HTML, which must never be kept).
- **Updates:** a new version installs, takes over at once, and keeps the previous build's cache so
  an open page can still load its lazy chunks. The page's status line (under the name) then offers
  a reload. Long-open pages check for a new version at most hourly when they come back into view.
- **Offline:** the status line says "Offline", drawing is off (legs need the routing service, and
  the basemap is not cached) and the panel says why, while uploads, plans and exports still work.
- **Headers:** `apps/web/public/_headers` (read by Workers static assets) serves `sw.js` and the
  manifest with `Cache-Control: no-cache` and hashed assets as immutable.
- **Tests:** E2E runs with service workers blocked (`playwright.config.ts`), since one would answer
  requests the tests stub. `e2e/tests/pwa.spec.ts` turns them on: manifest and icons, Chrome's
  installability check (`Page.getInstallabilityErrors`; Lighthouse 12 removed its PWA audits),
  precache contents, network-first reloads, the update prompt, an offline reload of an uploaded
  course with terrain tiles from the cache (`context.setOffline` with every stub removed), and the
  tile cache's bound. Safe-area insets are simulated with `Emulation.setSafeAreaInsetsOverride`.
- **Real phone:** see [docs/real-phone-checklist.md](docs/real-phone-checklist.md).

## Routing

`POST /api/route` (in `apps/worker/src/route.ts`) routes one leg on foot through hosted
OpenRouteService, holding the key server side. The request, response and error codes are the wire
contract in `packages/core/src/routing.ts`, with the `RoutingProvider` interface and
`httpRoutingProvider`, the client for it.

- **Key:** get a free one at <https://openrouteservice.org/dev/#/signup> (2,000 directions requests
  a day, 40 a minute). Set it as the `ORS_API_KEY` repository secret (`gh secret set ORS_API_KEY`),
  and the next deploy uploads it; or set it directly with
  `pnpm --filter @pp/worker exec wrangler secret put ORS_API_KEY`. For `pnpm dev`, put
  `ORS_API_KEY=...` in `apps/worker/.dev.vars` (gitignored).
- **Cache:** successful legs are cached for a week with the Cache API, keyed by profile and
  coordinates rounded to 5 decimals (about 1 m). The Cache API does nothing on `*.workers.dev`, so
  this only takes effect on a custom domain.
- **Rate limit:** 20 upstream (uncached) requests per client IP per minute, with the Workers Rate
  Limiting binding `ROUTE_RATE_LIMITER` in `wrangler.jsonc`. A counter in Worker memory would be
  per isolate, and so easy to exceed; the binding is shared within each Cloudflare location (and
  eventually consistent, so bursts can overshoot slightly). It does not cap the shared daily quota;
  ORS answers `upstream_rate_limited` once that is used up.
- **Fixtures:** the Worker tests replay `apps/worker/test/fixtures/ors/` and never call ORS. The
  committed files are synthetic until someone runs `ORS_API_KEY=... pnpm fixtures:record` (see the
  README there).

## Race library

`/races` (B13) lists the races in `apps/web/src/races/catalog.json`, seeded from
[docs/race-catalog.md](docs/race-catalog.md). Every fact (usual month, the main field's local start
time, time zone, distance, website) was checked on the race's own website; `verified` is the month
that happened, and a race with a fact that could not be confirmed has `verified: null` and names
it in `unverified`. The page is a route of the single-page app (`apps/web/src/router.tsx`): the
Worker's single-page fallback serves it online, and the service worker's cached shell offline.

A race with a course links to `/?race=<slug>`, which downloads `/races/<slug>.gpx` and loads it
like a picked file, then keeps the race in `AppState.race` (and the saved session) for race-day
conditions. To add a course, export the GPX (from Strava, say) and run:

```sh
pnpm races:add <slug> <file.gpx>   # --force to accept a length more than 1.5% off
```

It simplifies the track to within 2 m, checks its length against `distanceM`, writes
`apps/web/public/races/<slug>.gpx` and sets the race's `gpx`. `apps/web/test/races.test.ts`
checks the catalog and that every course parses and measures within 1.5%. E2E tests give a race a
fixture course with `window.__PP_RACE_CATALOG__` (an init script), so the shipped catalog needs
none.

## Reports

"Report a problem" (B12) is in the panel header's menu (on a phone, the sheet's top corner). It
files a bug or an idea as a GitHub issue in this repository, labeled `user-report` plus `bug` or
`idea`, through `/api/report` (`apps/worker/src/report.ts`; the wire contract is
`packages/core/src/report.ts`).

- **What a report holds:** the kind, the description (up to 4,000 characters), and an email only
  if the user checks "Show my email in the issue" (issues can be public, so it is never sent
  otherwise). "Include diagnostics" (on by default, with a preview) adds the app version (the git
  commit, set at build time in `apps/web/vite.config.ts`), browser, viewport, units, theme, plan
  inputs and the last 20 uncaught errors and unhandled rejections (`apps/web/src/report/errors.ts`,
  installed in `main.tsx`). "Include my course" (off by default) adds a share link.
- **Untrusted text:** everything the user wrote goes into the issue inside fenced code blocks no
  text can close, so it cannot mention anyone, load images or break the template; the title breaks
  every `@` (`apps/worker/src/issue.ts`).
- **Human check:** Cloudflare Turnstile, invisible unless Cloudflare wants an interaction. The
  site key is public: `vars.TURNSTILE_SITE_KEY` in `apps/worker/wrangler.jsonc`, which the app reads
  from `GET /api/report`. The secret is `TURNSTILE_SECRET`.
- **Rate limit:** 5 reports per client IP per hour, a sliding window kept in the `REPORT_LIMITS` KV
  namespace under a hash of the IP. The Rate Limiting binding `/api/route` uses only has 10 and 60
  second windows, and Durable Objects would rule out preview URLs; KV is eventually consistent
  across locations, so the `REPORT_RATE_LIMITER` binding (5 attempts per IP per minute) sits in
  front to bound what that could let through.
- **Until it is set up,** `/api/report` answers `503 not_configured` and the dialog says reporting
  is unavailable. To set it up:
  1. **GitHub token:** Settings, Developer settings, Fine-grained tokens, Generate new token.
     Repository access: only `jcj59/perfect-pace`. Permissions: Issues, read and write (nothing
     else). Then `gh secret set GITHUB_REPORT_TOKEN` (the next deploy uploads it), or
     `pnpm --filter @pp/worker exec wrangler secret put GITHUB_REPORT_TOKEN`.
  2. **Turnstile widget:** Cloudflare dashboard, Turnstile, Add widget. Hostname
     `hf-worker.workers.dev` (it covers the production and preview subdomains) and any custom
     domain; mode Managed. Put its site key in `vars.TURNSTILE_SITE_KEY` in
     `apps/worker/wrangler.jsonc` and merge that, and set its secret key with
     `gh secret set TURNSTILE_SECRET` (or `wrangler secret put TURNSTILE_SECRET`).
  3. The labels `user-report`, `bug` and `idea` already exist in the repository; issues need them.

## Dependencies

Renovate opens one grouped PR a week for minor and patch updates, which auto-merges when green.
Major updates, Playwright (baselines may need regenerating) and anything failing need review.
Prefer a few lines of code over a new dependency, and keep `@pp/core` free of runtime dependencies.
